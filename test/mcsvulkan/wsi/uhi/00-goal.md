# 00 · 目标

## 问题

输入层（`arena_event`）已经能把平台事件规整成“一次一个变化 + 一个时间戳”。
上面这一层要回答的是：

> 一堆各自独立的状态机，各自在某几帧之后喊“我识别出来了”，
> **凭什么只有一个能成为用户看到的事件？**

现状（见 test_glfw12 的 `click_recognizer` / `double_click_recognizer`）：
每个识别器自己在 `identify()` 里判断，谁先到谁先喊；双击永远输给单击；
“等一等再决定”这种知识散落在每个识别器的 `if` 里，无法检查、无法证明。

## 目标

**一串原始输入进去，每个通道每次交互至多一个语义事件出来，且恰好播报一次。**

可检验的三条：

1. **结构决定裁决**：你只写“谁并行、谁细化谁、谁和谁互斥”，
   “哪些东西需要裁决器”是编译期算出来的，不是运行期猜的。
2. **没有纠纷就不引入裁决**：键盘和鼠标互不相干，
   它们之间不排队、不延迟、不共享任何状态。
3. **坏结构编译不过**：跨通道的依赖、同一个事件两个生产者、自相矛盾的声明，
   都是编译错误，不是运行期断言。

## 不解决什么

| 不做 | 为什么 |
|---|---|
| 事件队列 / 背压 | 输入层已经按帧喂了；这一层只处理“一帧之内和跨帧的假设” |
| 线程 / 异步调度 | 一帧是同步的；cell 之间不相交，将来要并行也只需按 cell 分 |
| 控件 / 命中测试 | “点在哪个按钮上”是消费方的坐标问题，不是裁决问题 |
| 手势的**写法** | `click` 的 FSM 长什么样是你的事；库只规定它的**接口**（`step` 返回四选一） |

## 唯一的核心不变式

> **每 (通道, 一次交互) 至多一个 accepted；每次 accepted 恰好播报一次。**

注意它约束的是 **accepted**，不是“识别成功”。
识别成功只是提出申请；一次交互里可以有多个申请，但只能有一个答复是“是”。

## 为什么这一层值得单独做

因为两件事是正交的：

- **识别** = 状态机：`press → release → done`。它只关心自己，天然可组合、可单测。
- **裁决** = 关系图：谁细化谁、谁和谁互斥。它只关心别人，天然是全局的。

把两者塞进同一个类里，就会出现“每个识别器都要知道别人”的耦合（现状）。
分开之后，识别器不认识任何别的识别器，裁决器不认识任何识别器——
**它们只通过一条 claim（kind + 时间跨度）相遇。**
