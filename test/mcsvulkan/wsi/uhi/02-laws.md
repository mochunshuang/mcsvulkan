# 02 · 定律

六条。每条写三件事：**陈述 / 为什么成立 / 在哪验证**。
定律是这一层的骨架；实现可以换，定律不能破。

---

## L1 同态律（组合律）

**陈述**：把树的组合方式映射成 footprint 的合并方式，是一个同态。

```
F(leaf<K,S>)     = {K} , ∅
F(a || b)        = F(a) ∪ F(b)                      （不新增边）
F(a <|> b)       = F(a) ∪ F(b) + (a.kinds × b.kinds 对称边)
F(refines(a,b))  = F(a) ∪ F(b) + (a.kinds → b.kinds 有向边)
F(times(d, a))   = F(a)
```

**为什么成立**：footprint 只由“树的结构 + 每个 kind 的归属”决定，不依赖运行期。

**推论**：树的括号可以任意重排，只要“谁和谁组合”不变，语义不变。
这就是你说的“细分再组合，得到与源问题等价的结果”。

**验证**：`plan()` 的五个实现（leaf / all_of / one_of / refines / times）互相只通过
`operator+` 与“加边”合成，见 [uhi.hpp:120](v1/src/uhi.hpp#L120-L123)、
[:158](v1/src/uhi.hpp#L158-L158)、[:166](v1/src/uhi.hpp#L166-L181)、
[:189](v1/src/uhi.hpp#L189-L198)、[:206](v1/src/uhi.hpp#L206-L206)。

## L2 划分律

**陈述**：关系只存在于同 source 内；因此关系图按 (source, 连通分量) 分成**互不相交**的 cell，
整体语义 = 各 cell 语义的**积**。

**为什么成立**：
① `refines` / `one_of` 生成的边两端必须同源，否则编译错误（`validate`）；
② 不同 cell 之间没有任何边，也没有共享状态。

**推论**：cell A 里发生的事情，对 cell B 是完全不可观测的。
“键盘和鼠标谁先谁赢”不需要设计——它们本来就不同 cell。

**验证**：**S4**：`key` 在 `click` 还悬着时立刻播报，而 mouse cell 一个字节都没动。

## L3 唯一律

**陈述**：一个 cell 内，一次交互至多产生一个 `accepted`；一次 `settle` 至多播报一条 `accepted`。

**为什么成立**：`win()` 是全库**唯一**播报 `accepted` 的地方，而且它先把所有会与它竞争的槽
（`excludes` 或“细化它”）杀掉，再播报。所以“赢”与“清理”是一个原子动作。

**注意**：这是**运行期**保证。编译期保证的是“谁和谁竞争”这张表是否正确 —— 两件事不要混。

**验证**：S1–S4 每条断言的记录里，`acc` 一次交互只出现一次；`stage::win` 见
[uhi.hpp:553](v1/src/uhi.hpp#L553-L567)。

## L4 顺序律

**陈述**：一帧之内，`leaf.step` 的调用顺序不可观测。

**为什么成立**（三条一起才够）：
1. 每个 leaf 只写自己的 FSM，不写别人的；
2. 一帧内**不播报任何判决**（`feed` 先让所有叶子走完，再 `settle`）；
3. cell 之间不相交（L2）。

**推论**：`walk_leaves` 从左到右遍历只是实现细节，换成任意顺序结果相同。

**已知边界**：同一帧内两个**互斥**的 kind 同时 `done` 时，先处理的赢。
这个先后由“拓扑序 + 声明序”决定，是**可观测**的。但互斥的手势通常要求不同的输入
（click 要 release，drag 要 move），同一帧并列属于退化情形。
v1 记录这个边界，没有消除它（要消除得给每帧一个序号，见 [04](04-design-space.md)）。

**验证**：S3 两个方向（click 先 / drag 先），日志对称。

## L5 退化律

**陈述**：`|cell| = 1` 且无边 ⇒ 该 cell 无 deferred、无撤销、无裁决开销；
`done` 当帧即 `accepted`。

**为什么成立**：没有邻居就没有 `blocked`，没有 `excludes` 就没有清理对象；
`stage` 退化成“一个槽 + 一次播报”。

**推论**：可以用它判断“我到底需不需要裁决器”——看蓝图里是 `direct` 还是 `arbitrate`。

**验证**：**S1**：click 在 release 当帧播报，不等任何窗口（对照 S2 里同样的 click 要等 350ms）。

## L6 一义律

**陈述**：每个 `kind` 恰好一个生产者。

**为什么成立**：`leaf<K,S,Fsm>` 的 `K` 就是 kind；树里出现两次 ⇒ 同名 ⇒ `validate` 报编译错误。

**推论（很重要）**：既然一个 kind 至多一条活着的申请，状态就可以**按 kind 稠密索引**
（一 kind 一槽），于是
- 不需要 handle / 代际 / 槽位复用；
- 不需要容量上限；
- 不需要“陈旧判决”检查。

v1 的 `stage` 比 v0 的 `referee` 短一半，全部来自这一条。

**代价**：一个 leaf 不能产出两个 kind。如果需要（比如 drag 同时报方向），
要么拆成两个 leaf，要么放弃“一 kind 一槽”回到 handle 方案。见 [04](04-design-space.md) 未决项。
