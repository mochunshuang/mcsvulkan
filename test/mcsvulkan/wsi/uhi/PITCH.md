# uhi 是什么，凭什么值得看

> 写给"会私下验证"的程序员。每条主张都给了**怎么验**和**怎样会被证伪**。

---

## 一、电梯版（三句）

1. **你写的不是识别器，是声明**：一个 UI 事件 = 一个状态机 + 一行关系；"谁该赢"不由识别器决定。
2. **判决是一个 25 行的纯函数**：删到期、删退出、按"最具体先"挑赢家、连坐它的对手、扫到不动点。没有虚函数、没有堆、没有字符串比较。
3. **加一个事件 = 写一个 FSM + 加一行声明**；已有代码一个字不改。

一行话概括它到底做了什么：

> **把"谁该赢"这个并发问题，换成"在一张有限的关系表上做消除"这个数据处理问题。**

---

## 二、你已经在忍的六件事

| # | 典型写法 | 症状 | 本设计怎么消掉 |
|---|---|---|---|
| 1 | `GestureManager` 里一条 if-else 链 | 谁优先写在代码里，加手势就改 switch | 关系外置成表，判决只有一个实现 |
| 2 | `for (auto* r : recognizers) r->on_event(e)` | **容器顺序偷偷变成优先级** | `order` 是编译期算的拓扑序，不是容器顺序 |
| 3 | 每个识别器持有"我和谁互斥" | O(N²) 耦合，两边认知还会漂移 | 关系住在**格子**上，识别器不认识别人 |
| 4 | 结构不可枚举 | 只能黑盒喂事件测 | `describe<Tree>()` 打印关系/格/槽/大小 |
| 5 | 跨手势状态泄漏（旧载荷） | 下一次交互用了上次的数据 | 判决/静默清除都强制 `reset`，并有 I1 不变量 |
| 6 | 一个识别器卡死就永远占着 | 别的永远不落地 | `hold` 兜底：只判负、不发明赢家 |

## 三、三个动作（全部设计都在这里）

### 动作 1：输出归一

```cpp
enum class step_t { idle, active, done, aborted, hold };
```

不管你的识别器数到 3 次还是量了 100px，它对仲裁层**只说这五个字**。这一步是后面所有化简的前提：输入域有限了，判决才可能是表。

### 动作 2：关系外置

```cpp
using mouse = one_of< refines<click, dbl>, drag >;
//            ^ a~b           ^ c->d      ^ 与两者都互斥
```

编译期生成四样东西（全是 `static constexpr`，运行期只读）：

| 数据 | 含义 |
|---|---|
| `waits[i][j]` | i 是 j 的抽象版：j 活着时 i 不许赢 |
| `excl[i][j]` | i 与 j 不能共存 |
| `order[i]` | 同一帧都完成时的裁决次序（拓扑序 = 最具体先） |
| `hold[i]` | 候选活太久就不可能是它 |

**关键**：这些数据**不属于任何识别器**，它们属于"格子"（可能相遇的一组候选）。

### 动作 3：判决 = 消除到不动点

```
每帧：删到期 → 删退出 → 按 order 挑"没有任何抽象版还活着"的人
      选中即连坐（互斥的 + 比我抽象的）→ 反复扫到没有变化
```

`CanWin(i)` 依赖"还剩谁"，而"还剩谁"依赖"谁赢了" ⇒ **循环定义** ⇒ 必须迭代到不动点。有限（每轮至少少一个）⇒ ≤N 轮。

## 五、三个反直觉但关键的点

给读者省时间——这三处误解最容易让人以为设计有洞：

**① 表不是缓存，是命题。**
`waits[click][dbl]=true` 不是"加速查询"，是"click 是 dbl 的抽象版"这条**断言**。删掉表你就没有"互斥"这件事了，不是变慢。

**② `order` 不是遍历顺序，是语义。**
同一帧两人都完成，谁赢**完全由 `order` 决定**。改成声明顺序、内存顺序或哈希顺序，判决就变。所以它必须是结构算出来的常量。

**③ 被优先的识别器必须"早占位"。**
`refines<click, dbl>` 只在 **dbl 有活着的候选**时才挡住 click。所以 `dbl` 的 FSM 必须在第一次按下就返回 `active`（占位），而不是等到第二次按下。**这是识别器的义务**，漏了优先级静默失效——不报错。

## 六、代价（必须接受，否则这套抽象崩）

| # | 代价 | 为什么不能省 |
|---|---|---|
| 1 | 识别器输出必须归一成 5 个值 | 否则输入域无限，判决无法是表 |
| 2 | 关系必须两两 | "如果 C 成立才让 A 优先于 B"这种三项条件表达不了；正确做法是加一个 kind |
| 3 | 并列必须有语义次序 | 并列客观存在；没有次序就没有确定性 |
| 4 | 时间必须外部喂 | `帧数 ≠ 时间`；只有 `tick(now)` 推进时钟 |
| 5 | 被优先者必须早占位 | 否则细化关系挡不住人（静默失效） |

**不适用**：跨设备手势（双指缩放需要跨格状态）、带置信度/权重的判决、需要运行期改优先级（`order` 是编译期常量）。
